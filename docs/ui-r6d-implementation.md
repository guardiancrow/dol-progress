# UI-R6D実装報告

前提詳細を見ている利用者が、ゲーム内で達成したクエストの記録をその場で追加できるようにした。UI-R5B/Cの候補条件を維持し、候補外の対象には本人確認による手動登録を提供する。Ownerの実装レビューと実アプリでの確認を待つ。

基準HEADは`b6e413ae3f3b1e39eae0ec9ef50caa9654b48baf`、ブランチは`feat/ui-r6c-quest-navigation`。開始時に署名有効とclean状態を確認した。署名検証は既存のallowed_signersを参照して行った。commit・push・PR・Merge・Release操作は行っていない。

## 候補と手動の許可条件を分けた

| 確認種別 | 操作を提示する条件 | 確認UI |
| --- | --- | --- |
| `candidate` | UI-R5Bの厳格な候補で、UI-R6Cの明示的な前提確認が有効 | 既存の「前提『…』を達成済みにする…」。新しいチェックは不要 |
| `manual` | 開示中の直接前提で、対象がactive・実在・一意、選択プロフィールの確定した記録が未達成 | 「達成済みとして登録…」。本人によるゲーム内達成の確認チェックが必要 |

同じ対象には一つの操作だけを表示する。候補による登録が成立する場合は既存操作を優先する。確認を開いた後に種別を変換しない。既存の確認候補一覧には手動登録を追加していない。

手動対象の内部ID・GVDB IDは正の安全な整数で、それぞれマスター内で一意であることを確認する。inactive・欠損・ID不正・重複は保存対象にしない。有効なプロフィールや進捗の確定状態を確認できない場合にも保存しない。

親が未達成、候補不成立、複数前提、AND/OR不明、原文との不一致、自己参照・循環、地図・特殊クエストであることは、対象自身が有効な場合の手動登録を妨げない。構造診断は表示に残し、本人が達成したという確認とは別に扱う。`buildPrerequisiteReviewIndex()`と`derivePrerequisiteProgressReview()`は変更していない。

## 操作と保存を既存UI-R5Cへ統合した

既存の前提名セルから詳細を開き、必要な世代だけを明示的にたどる。未達成の直接前提で手動操作を選ぶと、同じ非モーダル領域でプロフィール名・対象名・GVDB ID・内部ID・現在の記録を確認できる。対象1クエストだけの登録と、既存条件で関連発見物が発見済みになる可能性を案内する。

手動の確認チェックは確認要求に属する。チェック操作でフォーカスを確認領域の先頭に戻さない。キャンセル・Escape・対象変更・プロフィール変更・マスター更新でチェックを破棄する。候補確認にはチェックを強制しない。

`PrerequisiteReviewConfirmation`を種別付きの要求にし、`QuestsPage`の既存確認状態・pending・共通ロック・`updateCompletion()`・`completeQuestWithLinkedDiscoveries()`を共用した。新しいDB更新APIやSQLを追加していない。

確定時は次の順に処理する。

1. 現在も同じプロフィール・マスター・進捗snapshot・読取世代・更新revisionで、要求種別の許可条件を満たすことを確認する。
2. 共通ロックを取得して最新の達成済みIDを一括取得する。読取失敗なら保存せず、再読み込みへ案内する。
3. 待機中に世代や条件が変わっていないことを再確認する。既登録ならAPIを呼ばず最新記録を表示する。他の進捗だけが変わった場合も、確認を引き継いで保存せず再確認を求める。
4. 対象1件を達成済みにする方向で既存APIを呼ぶ。トグル反転や`markIncomplete()`を呼ばない。
5. 保存応答後に達成済みIDを一括再取得し、同じ世代の結果から表示と候補を再計算する。既存の地図状態再取得と、例外時の回復用再取得も維持する。

確認中の詳細切替・段階移動、保存中の二重操作・閉じる・キャンセル・通常一覧からの競合保存を抑止する。プロフィール切替自体は許可し、旧世代の応答を新しい画面へ反映しない。登録後に別の前提へ自動移動しない。対象の登録ボタンが消えた場合は残っている詳細の「閉じる」へフォーカスを戻す。

## 保存結果と現在の表示を区別する

| 結果 | 表示と処理 |
| --- | --- |
| 前読取で対象が既登録 | 保存APIを呼ばず、最新記録と「再登録はしていません」を表示 |
| `questChanged=true`、再取得でも対象の記録を確認 | 新規登録完了。必要ならAPIが返した発見物登録件数を通知 |
| `questChanged=false`、再取得でも対象の記録を確認 | 既登録として表示し、新規成功を通知しない |
| `InvalidSelection` | 既存Rust処理の書込前拒否・rollback完了を示す応答として、保存拒否を表示。回復用再取得を行う |
| その他のAPI例外 | 保存状態未確認。回復用再取得が達成済みでも元の保存成功を推定しない |
| 保存応答後の再取得失敗 | 新規保存応答／既登録応答と、現在の進捗が未確認であることを分けて表示 |
| 世代変更・古い応答 | 別プロフィールや新しいマスターへ反映せず、必要な再取得を既存管理へ依頼 |

`DatabaseError`などの粗いエラーからcommitの成否を判断せず、自動再保存しない。通常一覧でも`questChanged=false`を受けた場合は最新進捗を再取得し、「既に達成済み」と通知する。通常一覧の新規登録と発見物件数の既存通知を維持する。

Rustの連動処理は変更していない。activeな関連発見物だけを既存条件で登録し、特殊クエスト・レリックの報告状態とカード状態の初期化規則を維持する。既存発見物の進捗・メモ等を上書きしない。既登録クエストへ発見物を後から補完する処理も追加していない。

## 一覧と情報開示の範囲を維持した

9列、空欄セル、前提名の列挙、入口の文字列・色・読み上げ名・行高を変更していない。新しい状態バッジや件数を入口に追加していない。後継探索・自動展開・目標保持を復活させていない。既出IDへの遷移を止めるUI-R6Cの循環対策を維持する。

確認画面の対象情報は開示済みの直接前提に限定する。`MasterInfoPopover.tsx`は変更せず、備考・説明・未知の祖先や後継・発見物名を確認UIやaria属性へ追加していない。閉じた詳細の内容はDOMに残さない。候補一覧の既存表示範囲は維持する。

## Ownerによる確認手順

1. 開発版でプロフィールを確認し、達成記録の抜けた中間クエストを持つ系列の前提名セルを開く。
2. 必要な前提だけを一世代ずつ開く。未達成の親の下でも、その直接前提に「達成済みとして登録…」があることを確認する。
3. 手動確認でプロフィール・対象名・両ID・未達成記録を確認する。チェック前には確定できず、キャンセルやEscapeで保存されないことを確認する。
4. ゲーム内達成を確認した対象だけにチェックし、登録する。対象1件だけが記録され、別の前提へ自動移動しないことを確認する。
5. 登録後の状態を確認し、必要なら次の前提を明示的に開く。既に達成済みの対象には登録操作がないことを確認する。
6. 厳格な確認候補がある関係では既存操作が一つだけ表示され、手動の確認チェックを要求しないことを確認する。
7. 確認途中にプロフィールを切り替え、確認・履歴・チェックが失われることを確認する。800×600と文字倍率200%でTab・Space・Enter・Escapeと内部スクロールを試す。

## 残る制約

ゲーム内達成や受注条件は照合できない。手動登録は本人の確認に基づく記録追加であり、AND/ORや系列全体の達成を判定しない。複数前提の一括登録や未達成への変更も追加していない。

保存前の読取と既存APIのtransactionは別であり、外部からのDB直接変更まで原子的に防ぐ保証は追加していない。既存APIのactive確認と冪等性を利用し、`questChanged=false`を新規登録と区別する。マスターやプロフィールのアプリ内更新では世代照合を行う。未知のcommit結果は未確認のままとし、再取得後の本人確認に委ねる。
