# UI-R6C 実装報告とOwner確認手順

クエスト一覧から単一の目標を開き、前提・後継を一段ずつ確認し、ゲーム内での達成を明示登録できるようにした。実装とローカル検証の対象であり、Ownerの画面・操作確認は未実施である。commit・push・PR・Release操作は行っていない。

## 作業基準と設計の引継ぎ

origin/mainを取得し、mainを`0c21ffa`へfast-forwardした。clean状態から新規ブランチ`feat/ui-r6c-quest-navigation`を作成した。以前の`feat/prerequisite-review-completion`の再利用・マージは行っていない。バージョンは0.5.0のままである。公開済みタグ、署名、正式ソース、Release、配布成果物、Release用スクリプトと通知入力は変更していない。

既存成果の`tmp/ui-r6a-review/design.md`と、そこで提案されたUI-R6B案、既存の前提判定・UI-R5B/Cのテストを確認した。独立したUI-R6B報告は、確認したリポジトリ内の文書では見つからなかった。今回のOwner方針を実装範囲の決定として扱い、設計報告が保留していた操作と寸法を実装・検証した。機能仕様は[要件定義](requirements.md)の「クエストの前提・後継ナビゲーション（UI-R6C）」に記載した。

## ナビゲーションの操作と状態

一覧の「関係」列から「前提・後継」を開く。選んだクエストが一時的な目標となり、直接の前提と直接の後継候補を表示する。「さらに前提」「さらに後継」で移動しても目標を保持し、移動方向を含む経路と現在位置、GVDB ID・内部IDを示す。「一つ戻る」「目標へ戻る」で以前の位置を確認できる。目標・経路は永続化しない。

達成記録は「達成済み」「未達成」、関係や条件の不確かさは理由付きの「要確認」として別々に示す。後継へ移動すると、そのクエストに合流する他の前提も確認できる。分岐・合流は直接関係と各クエストの前提・後継件数で把握する。巨大なツリー、自動展開、自動経路選択は追加していない。

関係一覧は方向ごとに10件ずつ表示する。索引と目標の前提探索結果はマスター世代ごとに再利用し、開閉・移動ではDBを再取得しない。目標の前提集計は5,000ノード・20,000関係で打ち切り、その場合は件数に「以上」と全体が未確認である説明を添える。直接関係のページ操作は続けられる。

## 確定できることと判定を保留すること

| 対象 | 表示・扱い |
| --- | --- |
| 選択プロフィールの達成記録 | 現在の取得世代で達成済みIDを照合する。保存・再取得中や取得失敗を未達成と確定しない |
| マスターに記録された関係 | 正規化された関係と元データの数値参照を、出所を保持して表示する |
| 既存の前提状態 | 既存の4状態をそのまま使用する。フィルターの判定を変更しない |
| 複数前提 | 各記録を表示し、すべて記録済みでもAND/ORは未確定とする |
| 地図・追究・レガシー等 | 関係と確認理由を表示する。パネルからの通常クエスト達成登録は提供しない |
| inactive | 履歴の関係として表示する。パネルからの新しい達成登録は提供しない |
| スキル・名声・国籍・発見物等 | 未照合と明示する。後継候補を受注可能と判定しない |
| 欠損・不正参照 | 分かるIDと理由を表示する。欠損先のマスターを作らない |
| 元データだけの関係・片方向不一致 | 関係を表示し、判定の根拠にせず要確認とする |

通常クエストの前提が要確認でも、利用者がゲーム内で達成した事実を記録する操作は提供する。これは受注条件の充足を確定する操作ではない。IDが不正・重複して対象を一意に識別できない場合は、パネルから登録しない。

## 分岐・合流・循環と大規模データ

同じ向きの同じIDの組は一つの辺へまとめ、重複があった事実は確認理由として残す。同名の別IDは別のクエストとして扱う。合流しても前提集計の同じクエストを二度数えない。

強連結成分を反復処理で求め、循環に属するクエストと、その後継で影響を受けるクエストを区別する。既存の前提判定とUI-R5Bの診断は書き換えない。関係をたどって経路内の既出位置へ戻った場合は、その位置まで履歴を戻す。循環で履歴を増やし続けない。

索引構築・循環検出・影響伝播はMap・Setと反復処理を使う。隣接リストはマスター順で一度整列する。前提集計は上限付きで行い、画面には各方向10件だけ描画する。30,000ノードの系列を使ったテストで、深い系列の探索と打ち切りを確認した。

## 達成登録と保存後の再計算

「現在のクエストの達成を登録…」でインライン確認を開く。プロフィール、対象名とID、関連発見物が既存条件で発見済みになる可能性を説明し、確定した場合だけ保存する。確認開始時と確定直前に世代・snapshot・読取・更新状態を照合し、状態が変わった確認からは保存しない。

保存には既存の`updateCompletion()`と`completeQuestWithLinkedDiscoveries()`を使う。対象1件だけを選択プロフィールへ登録し、他の前提・後継を達成済みにしない。通常一覧からの競合操作と二重確定を抑止する。発見物連動、既存進捗を上書きしない条件、Rustのtransactionは変更していない。

保存成功後は達成済みIDを一括再取得する。同一プロフィール世代・マスター世代・更新revision・読取世代であることを確認してsnapshotを更新し、前提状態・未達成件数・後継の関連表示・既存の進捗確認候補を再計算する。保存完了と再取得完了が確認できたときだけ、関連表示を更新した旨を通知する。表示の更新で別のクエストへ自動移動しない。

保存の結果不明は成功と通知しない。回復用の再取得で達成済みになっていても、元の保存の成功は断定しない。保存成功後の再取得失敗は保存失敗と分けて表示し、未確認の計算結果を表示しない。プロフィールA→B→Aの切替、保存中のマスター再取得、保存後の遅延した進捗取得を検証した。古い処理から現在の表示と成功通知を更新しない。

## 既存機能と変更ファイル

UI-R5Bの「前提クエストの進捗確認候補」は、達成済み後続の記録漏れ確認という既存の役割と条件を保つ。新しいパネルとは同時に展開せず、両方の確認・保存中に領域を切り替えて処理を破棄しない。正常な開閉・移動・保存後の再取得では、一覧の検索・フィルター・並べ替え・ページ位置・件数・テーブルDOMを保持する。再取得失敗で一覧を隠す既存の安全動作は維持した。

進捗の保存先、同意、バックアップ、Data Root移行、配布処理、アプリの通信方針は変更していない。DBスキーマ・migration・import形式・Rustコード・依存関係・ライセンス・バージョン番号の変更はない。今回のライセンス監査対象差分はない。

## Ownerによる画面・操作確認手順

1. 開発ブランチで`npm run tauri dev`を起動し、確認用プロフィールを選ぶ。既存データを使って達成登録を試す場合は、通常のバックアップ手順で先に保全する。
2. 画面を800×600にし、クエストを検索する。「関係」列の「前提・後継」を開き、目標名・現在位置・IDと直接前提／後継候補を確認する。
3. 「さらに前提」で複数階層をたどる。「一つ戻る」「目標へ戻る」で目標を保持したまま戻れることを確認する。
4. 分岐した系列では各分岐をたどり、合流するクエストへ移動して他の前提も表示されることを確認する。
5. 複数前提・地図・特殊クエスト・inactive・参照欠損等がある場合は、達成記録と「要確認」の理由が別々に表示されることを確認する。後継候補が受注可能と表示されないことも確認する。
6. ゲーム内で達成済みの通常クエストについて、対象位置の「現在のクエストの達成を登録…」を開く。プロフィール、名前・ID、発見物連動の説明を確認し、まずキャンセルする。記録が変わらず、起点へフォーカスが戻ることを確認する。
7. 登録する場合は再度確認して「達成済みにする」を実行する。保存結果の表示、一覧の対象チェック、未達成件数、関連する前提・後継の状態を確認する。他のクエストが自動達成されていないことを確認する。
8. 検索・フィルター・並べ替え・ページ位置・表示件数を設定し、パネルの開閉・移動・保存の前後で保持されることを確認する。パネル内とテーブル内のスクロール、通常一覧のページ送りを試す。
9. 「検索・フィルターを隠す」でテーブル優先表示へ切り替え、同じ操作を試す。文字倍率200%でもパネルの内容と確認操作へ到達できることを確認する。
10. Tab・Enter・Spaceで開閉・移動・確認を操作する。Escapeは確認のキャンセルを優先し、次のEscapeでパネルが閉じることを確認する。Tabでパネルから一覧へ移動できることも確認する。
11. 既存の「進捗の確認候補」がある場合は、新パネルと切り替える。確認中・保存中の切替が抑止され、確認候補の判定と個別登録が従来どおりであることを確認する。
12. プロフィールを切り替え、目標・経路・確認が解除され、別プロフィールの達成記録になることを確認する。マスターを更新した場合も、以前の目標を引き継いで保存しないことを確認する。

保存・読取失敗、遅延応答、循環や欠損は合成データの自動テストで再現している。Ownerの確認のために実DBを壊したり、故意に不正なCSVを取り込んだりする必要はない。

## 残る制約

受注条件、複数前提のAND/OR、特殊条件、現実の全系列の完全性は引き続き未確定である。実データの欠損を修復・補完する機能は追加していない。目標をまたぐ最短経路、複数目標の永続管理、グラフィカルツリーは対象外である。

取得世代の照合は、既存のDB APIへ原子的な競合制御を追加するものではない。実行中のアプリ以外からのDB変更まで保証を広げない。マスター世代やプロフィールが変わった場合は以前の目標を解除して再確認する。

Ownerの実装レビューと実アプリでの画面・操作確認を待つ。公開や次版のRelease準備は別作業とする。
