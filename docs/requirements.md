# 要件定義

## 1. 文書の目的

本書は、「大航海時代 Online」のクエストおよび発見物の進捗をローカルで管理する
デスクトップアプリケーションの機能要件と非機能要件を定義する。

DBの具体的な列定義は `database-design.md`、GVDB公開データの取り込み方法は
`data-import.md` を正とする。

## 2. 背景

「大航海時代データベース（GVDB）」には、クエスト情報や発見物情報など有用な
マスターデータが公開されている。

利用者向け表示とREADMEではサイト名を「大航海時代データベース」に統一し、略称を併記しない。
内部識別子（`gvdb_id`等）、CSV互換性に関係する名称、固定URLは変更しない。

一方、キャラクターごとのクエスト達成状況や発見物の進捗は、長期間にわたって
自分自身で保持したい情報である。

本アプリケーションは、GVDBの公開マスターデータをローカルへ取り込み、
ユーザー固有の進捗情報はローカルSQLiteへ永続保存することで、この用途を実現する。

本アプリケーションはGVDBの代替サイトを目的としない。また、GVDBへの書き込みや
不要なアクセスを行わない。

## 3. 対象環境

### 3.1 初期ターゲット

- Windows 10／11 x64デスクトップ
- 単一ユーザー
- ローカル利用

GitHubのPublicリポジトリでソースコードを公開し、Windows x64 Portable ZIPをGitHub Releasesで
配布する方針とする。アプリは個人のPCでローカル利用し、インストーラーを必要とせず、
完全終了後のフォルダー全体のコピー・移動で利用できる構成を維持する。
実際のPublic化・配布は本人の別途承認による。文書の整備を公開済みの事実認定とは扱わない。

第三者通知の正式レビューと既存HEADのRelease／Package／独立Verifierの技術検証は完了済みである。
SDK受領者条件をREADMEとConsent v2へ実装しているが、同程度の保護と合意方式の契約解釈、
MSVC startupの個別再配布根拠、配布者の補償等の本人判断は未完了である。
文面の実装を契約適合性やバイナリ公開の承認と扱わない。配布候補の生成には署名済みclean sourceと既存gateを
使用し、通常のローカル開発とは区別する。現行状況と工程は[Release手順](release-build.md)を参照する。

### 3.2 通常利用時の前提

- インターネット接続を必要としない。
- SQLiteデータベースはユーザーPC上に保存する。
- GVDBマスターの更新は、ユーザーが手動で取得したファイルを明示的にインポートする。

### 3.3 外部Runtimeと起動前検査

Windows/MSVCでは動的CRT方式を正式なローカル開発構成とする。`build.rs`でCargo target
OS=windows／env=msvcの場合だけ、`tauri_build::build()`より前に`STATIC_VCRUNTIME=false`を
設定し、Tauriの静的CRT強制を解除する。Microsoft Visual C++ Redistributable x64（v14系）を
外部要件とし、ビルド時のMSVCツールセットと同じか新しい互換版を使用する。固定の旧版を
最低条件として指定しない。アプリによるRedistributableの自動取得・導入は行わない。
VC++ Runtime DLL不足ではRust entry前にWindowsローダーが起動を失敗させる場合があり、
以下のアプリ内WebView2検出・日本語案内を保証できない。
Windows標準のUCRT等のOS提供DLLへの依存は許容する。SQLite bundledとWebView2 Loader
static libraryはEXE内への静的リンクを維持し、個別インストールを要求しない。
SQLiteの静的ライブラリ化とCコンパイル時のCRT選択は別であり、最終EXEのimportsと
リンク診断を確認する。全Rustターゲットへの追加RUSTFLAGSやcrt-static設定は導入しない。
WebView2 Runtimeは外部前提条件とし、自動導入や独自bootstrapperを追加しない。
portable data/config仕様は維持する。

画面表示にはMicrosoft Edge WebView2 Runtimeが必要である。Rust entryで3.4の多重起動判定を通過した後、既存Tauriの
`tauri::webview_version()`で利用可能versionを取得し、成功した場合だけportable filesystem
preflight、Tauri Builder、WebView生成、setup/DB初期化へ進む。Loaderが正常に返すchannel付き
versionも許可し、アプリ独自のchannel拒否やminimum version判定は行わない。

検出error、空・空白のみ・制御文字を含む返値は利用不能として扱い、data/configの作成・probeや
DB初期化を行わない。WebViewに依存しない日本語native dialogでMicrosoft公式のWebView2
Evergreen Runtime導入と再起動を案内し、OKでexit code 1として終了する。案内URLはRustの
`runtime_preflight`に一度定義する。browser自動起動、Runtime自動download/install/update、
registry/file探索による独自検出は行わない。versionや検出errorをDB/config・通常ログへ保存しない。

この検査は起動前のprerequisite確認であり、WebView生成成功の保証ではない。検査後の環境変化や
environment生成失敗に対する既存Tauriのfallback処理は維持する。WebView2 UDFは現行LocalAppData
defaultのままとし、アプリ所有のdata/configとは区別する。

### 3.4 Windowsの多重起動防止

Windowsでは`main.rs`の最初の処理で、固定名`Local\com.dolprogress.manager.single-instance`の
名前付きMutexを生成する。`CreateMutexW`の戻り値と直後の`GetLastError`で判定し、
`ERROR_ALREADY_EXISTS`なら通常起動へ進まない。作成失敗も排他成立とみなさず停止する。
両方とも既存のnative error表示を使い、重複時は「アプリケーションは既に起動しています。」と通知してexit code 1で終了する。
後続プロセスはWebView2検出・同意設定の確認や保存・Data Root準備・DB初期化・migrationへ到達しない。
通知以外の新しいアプリウィンドウを生成せず、先行プロセスのデータや画面状態を変更しない。

`bInitialOwner=FALSE`とし、スレッドによる所有・待機・`ReleaseMutex`は使用しない。
先行プロセスは`run()`全体を囲むguardでハンドルを保持し、通常終了・unwindでは`OwnedHandle`が閉じる。
process終了時はOSもハンドルを閉じ、最後のハンドルが閉じるとオブジェクトが消滅する。
後続プロセスが開いたハンドルも通知前に閉じる。使用許諾の起動時leaseは従来どおり別に管理する。

排他は同一Windowsセッションのアプリ単位である。新方式を実装した同じidentifierのバイナリは、
Debug／Release、EXE配置、CWD、Data Rootが異なっても並行起動を抑止する。
異なるData Rootごとの並行起動、既存ウィンドウの前面表示・最小化復元は提供しない。
Mutex未実装の旧版、別Windowsセッション、別identifierや外部ツールからのDB操作には適用されない。
旧版との混在やSQLite操作全体の安全を保証するものではない。
固定名を他プロセスが先に作った場合やアクセス権の問題でも起動を拒否する可能性がある。
Windows以外にはこの排他を追加しない。

## 4. ドメイン用語

### 4.1 プロフィール

本アプリケーションにおける「プロフィール」は、ゲーム内の1キャラクターを表す。

1つのアカウントに複数キャラクターが存在する場合でも、進捗はキャラクター単位で
独立して管理する。

v1ではゲームアカウントそのものを別エンティティとして管理しない。

### 4.2 クエスト

GVDBの `quests.csv` に含まれる1レコードを、本アプリケーション上のクエスト系
マスターとして扱う。

GVDB上で「地図」等として扱われるレコードも、`quests.csv` に含まれる限り
同一のマスター集合として管理する。

### 4.3 発見物

ゲーム内の発見物を表す。

発見物には少なくとも次の状態が存在する。

- 未発見
- 発見済み・未報告
- 報告済み

### 4.4 発見物カード

発見物に付随するカードの現在の所有状態を表す。

カード所有状態は、発見済み／報告済みと独立して管理する。

カードは失う場合があり、再取得する場合もある。

v1ではカードの取得・消失履歴そのものは管理しない。

### 4.5 マスターデータ

GVDB公開データから取得・更新される情報。

主な対象:

- クエスト
- 発見物
- 発見物分類
- クエストと発見物の関連
- クエスト前提関係
- クエスト必要スキル
- クエストの個別オファー都市

### 4.6 ユーザーデータ

ユーザーが本アプリケーション上で作成・更新する情報。

対象:

- プロフィール
- キャラクター別クエスト進捗
- キャラクター別発見物進捗
- 報告状態
- カード所有状態
- ユーザー入力メモ

マスターデータ更新によってユーザーデータを失ってはならない。

## 5. 機能要件

## 5.1 プロフィール管理

アプリケーションは以下を提供する。

- プロフィールの作成
- プロフィール名の編集
- プロフィールの削除
- プロフィールの切り替え
- 任意メモの保存

プロフィールを削除する場合、そのプロフィールに属する進捗を削除してよい。
ただしUIでは明示的な削除操作として扱い、誤操作しにくい設計とする。

## 5.2 クエスト一覧

選択中プロフィールに対し、マスターに存在するクエスト系レコードを一覧表示できる。

少なくとも以下を表示可能とする。

- クエスト名／地図名
- 難易度
- オファー方法
- オファー都市
- 必要スキル
- 関連発見物
- canonicalな`quest_dependencies`に直接登録された前提Questの名称（地図等を含む）
- 達成（クエスト達成記録）

前提Questの名称表示は直接関係だけを列挙し、再帰的な祖先、AND/OR、達成状態を解釈・表示しない。

GVDBマスターの備考に内容がある行は、名前セルの情報ボタンからクエスト名を見出しとする
ポップアップで備考全文を参照できる。NULL・空文字・空白のみの備考ではボタンを表示しない。

関連発見物列でも、各発見物名の横に情報ボタンを表示し、発見物一覧と同じ説明・備考を参照できる。
両方がNULL・空文字・空白のみの場合はボタンを表示しない。詳細は既存の関連発見物一括取得に含める。
クエストと各関連発見物を別々の識別キーで管理し、同じIDや複数クエストで共有する発見物も混同しない。
共通ポップアップの開閉・フォーカス・スクロール・ページ変更時の扱いに従い、進捗は変更しない。

非アクティブなマスターの扱いはUI設計時に決めるが、データベースから物理削除しない。

## 5.3 クエスト進捗

プロフィールごとにクエスト達成状態を保持する。

状態モデルは次の通りとする。

- `quest_progress` に行が存在しない: 未達成
- `quest_progress` に行が存在する: 達成済み

v1ではクエスト進捗に「未報告」という状態を持たせない。

達成済みから未達成へ戻す操作も可能とする。

## 5.4 発見物一覧

選択中プロフィールに対し、発見物を一覧表示できる。

一覧の対象は概要の件数と同じくactiveな発見物とする。inactiveなマスターとその進捗は保存したままとする。

少なくとも以下を表示可能とする。

- 発見物名
- 発見物分類
- ランク
- 説明
- 時代
- ポイント
- 難易度
- 経験値
- 関連クエスト
- 発見状態
- 報告状態
- カード所有状態

説明または備考に内容がある行は、名前セルの情報ボタンから発見物名を見出しとする
ポップアップを開き、「説明」「備考」を別々に表示する。空の項目は表示せず、両方が
NULL・空文字・空白のみならボタンも表示しない。クエスト・発見物のポップアップは
GVDBマスター情報だけを扱い、プロフィールごとのmemoを含めない。

関連クエスト列でも、オファー都市または備考に内容がある各クエスト名の横に情報ボタンを表示する。
オファー都市はマスターの`quests.offer_city`を半角カンマで分割し、前後の空白・空要素・重複を除き、
出現順に「、」で全都市を表示する。ゲーム内の取得方法を推測して補完しない。
クエスト一覧と同じ備考全文を表示し、オファー都市と備考の空の項目は省略する。
両方ともNULL・空文字・空白のみならボタンを表示しない。都市情報だけでもボタンを表示する。
都市と備考は既存の関連クエスト一括取得に含め、ボタン操作による追加DB照会は行わない。
発見物と各関連クエストを別々の識別キーで管理し、IDが一致しても内容を混同しない。
発見物の情報ボタンと共通のポップアップを使い、テーブル全体で同時に1件だけ開く。

ポップアップは各テーブルで1件だけ開き、同じボタンで閉じ、別行のボタンで内容を切り替える。
Escape・外側クリック・閉じるボタンで閉じ、Escapeと閉じるボタンでは可能な場合に元の
情報ボタンへフォーカスを戻す。Enter／Spaceで開け、ページ・検索／絞り込み・ソート・
プロフィールの変更や対象行の消失でも閉じる。ボタン付近の配置を画面内へ調整し、長文は
内部スクロールと折り返しで全文を読める。改行を保持した通常のReactテキストとして描画し、
選択・コピーを許可する。HTML解釈、URLの自動リンク化・外部アクセスは行わない。

## 5.5 発見物進捗

プロフィールごとに発見物進捗を保持する。

状態モデルは次の通りとする。

- `discovery_progress` に行が存在しない: 未発見
- 行が存在し `reported = 0`: 発見済み・未報告
- 行が存在し `reported = 1`: 報告済み

上記は保存状態を示す。表示・集計には後述の「特殊クエストの自動報告」による有効な報告状態を使用する。

ただし、種別が`レリック`の発見物は報告対象外である。レリックは行の存在を発見済みかつ最終状態として扱い、`reported`の保存値を未報告または報告済みとして表示・集計しない。

発見済みから未発見へ戻す操作も可能とする。

未発見へ戻した場合、その発見物の `discovery_progress` 行を削除する。

## 5.6 カード所有状態

発見済みの発見物について、カードの現在所有状態を保持する。

- `card_owned = 1`: 所有
- `card_owned = 0`: 非所有

報告状態とカード状態は独立して変更できる。

新たに発見済みとして登録する通常操作では、ゲーム仕様に合わせ
`card_owned = 1` を初期値とする。ただしユーザーは直後に非所有へ変更できる。

ただし、種別が`レリック`の発見物はカード対象外である。レリックは`card_owned`を表示・集計せず、新規発見時には`card_owned = 0`を保存する。レリックの報告・カード操作は提供しない。

### 特殊クエストの自動報告

特殊クエストは、`quests.offer_method`が`追究クエスト`、`レガシー`、`トレジャーハント`のいずれかに完全一致するものとする。発見物分類とは独立して判定する。

- Quest達成による新規Discovery登録では、そのQuestが特殊クエストなら非レリックを`reported = 1`、それ以外は`reported = 0`で保存する。
- Discovery側の連動では、activeな関連Questが唯一ならそのQuest、複数ならユーザーが選んだQuestを基準とする。関連なし・複数で未選択の場合は推定せず`reported = 0`で保存する。
- 既存の進捗は報告値・カード所有・メモ・更新日時を含めて書き換えない。マスター更新時の補正や一括backfillも行わない。
- 表示・絞り込み・Overview・冒険勲功値に使う「有効な報告状態」は、発見済みの非レリックで、activeな関連Questが唯一かつ特殊Questの場合に報告済みとする。それ以外は保存済みの`reported`を使う。非activeな関連Questは判定件数に含めない。
- この条件に該当する非レリックは「報告済み（自動）」と表示し、手動報告操作を表示せず、Rust側でも報告値の変更を拒否する。カード所有は従来どおり独立して操作できる。
- 「自動」は現在のマスターから導出した状態であり、登録経路の履歴を保証しない。複数関連の場合、特殊Questを選んで`reported = 1`を保存していても「自動」とは表示せず、通常の報告操作を許可する。登録経路は永続化しない。
- レリックは全規則に優先して報告・カード対象外とし、新規保存値は`reported = 0`、`card_owned = 0`とする。発見済み件数には含める。
- 新規登録後のDiscovery一覧は保存済み進捗を再取得する。保存値と有効な報告状態は区別し、派生表示のためのユーザーデータ更新は行わない。

冒険勲功値はプロフィール別に、初回報告確認済み、旧参考値の引継ぎ資格あり、現在発見済みかつ特殊自動報告対象、の発見物IDの和集合から算出する。同じ発見物は一度だけ数え、レリックを除外し、非active発見物も含める。経験値NULLは合計に加えず、不明件数に含める。現在の未報告・報告済み件数は従来の有効報告状態で集計する。トレジャーハントの非レリックにもこの規則を適用するが、調査CSVの該当8件についてゲーム内での勲功付与は未検証であり、今回の仕様上の仮定とする。調査件数を判定の固定値には使用しない。

## 5.6.1 クエスト・発見物進捗の正方向連動

クエストと発見物の進捗連動は、ユーザーが未達成から達成、または未発見から発見済みへ
変更したイベントに対する入力補完とする。DB全体を常に同期させる制約ではない。

- Questを達成済みにしたときは、そのQuestに直接関連するactiveな発見物のうち未発見のものを、
  同一transactionで追加する。非レリックは発見済み・カード所有とし、報告状態は上記の特殊クエスト規則に従う。レリックは発見済み・報告対象外・カード対象外とする。既存の発見物進捗は
  `reported`、`card_owned`、`memo`を含めて変更しない。
- Discoveryを発見済みにしたとき、直接関連するactiveなQuestが1件なら同一transactionで
  達成済みにする。2件以上なら、ユーザーが1件または「クエスト進捗は変更しない」を選んで
  から保存する。選択したIDは保存時にもactiveな直接関係であることを検証する。
- Discoveryから自動達成したQuestを起点に、別のDiscoveryへ再帰的に連動してはならない。
- Questを未達成へ戻してもDiscovery progressを削除しない。Discoveryを未発見へ戻しても
  Quest progressを削除しない。報告状態とカード所有状態の変更もQuestへ連動しない。
- 自動連動は操作開始時に選択されていたプロフィールだけへ適用する。

Master Importによる関係更新時の再同期および既存進捗の一括backfillは行わない。

## 5.7 検索

少なくとも以下を検索できる。

- クエスト名／地図名
- 発見物名

v1ではSQLiteの通常検索を使用し、FTS5は必須としない。

## 5.8 絞り込み・並べ替え

少なくとも以下の絞り込みを提供できる設計とする。

### クエスト

- 達成／未達成
- 前提クエスト充足（選択中プロフィールのdirectな依存関係から導出）
- オファー方法
- 個別オファー都市（複数都市を含む元文字列を分割した各都市）
- 必要スキル名（rank条件は扱わない）
- 関連発見物の有無と分類（`quest_discoveries`を正本とする）

オファー方法は個別値に加え、大分類「クエスト」「地図」を選択できる。
「クエスト」は`冒険クエスト`・`交易クエスト`・`海事クエスト`のexact OR、
「地図」は`地理学`・`考古学`・`宗教学`・`生物学`・`美術`・`財宝鑑定`・`天文学`のexact ORとする。
他の個別オファー方法も維持し、大分類判定には名称の部分一致を使用しない。

関連発見物はDiscovery側の`関連クエスト`から構築されたrelationで判定し、Quest側の
`発見物`・`発見物種類`の原文から推測しない。「発見物あり」はrelationが1件以上、
「発見物なし」は0件を指す。分類はlinked Discoveryのいずれかが一致すれば対象とし、
inactiveな発見物へのrelationも含む。分類候補は一覧マスター全体のlinked分類から生成する。

前提クエスト状態は保存せず、Quest masterの依存関係と選択中プロフィールの達成状態から
`NONE`（前提edgeなし）、`SATISFIED`、`UNSATISFIED`、`UNKNOWN`を導出する。
通常Questの単一前提のみ完了／未完了を確定判定する。複数前提はAND/ORの組が
machine-readableではないため、通常Questの全前提が完了した場合のみ`SATISFIED`、
一部または全部が未完了なら`UNKNOWN`とする。地図等の特殊前提、欠損・不整合のある関係も
`UNKNOWN`とする。「前提を満たす」は`NONE`または`SATISFIED`を指し、スキル・名声・
国籍等を含む「受注可能」を意味しない。recursive ancestorの進捗整合性監査は別機能である。

必要スキルのうち名称が `語` で終わるものは、rankではなく習得の有無を要求する
language skillとして扱う。
必要スキル名を選択した場合、そのスキルの正規化された要求rankを数値で低い順・高い順に
並べ替えられる。数値rankを持たないスキルでは並べ替えを利用できない。rankが未記載の行は
両方向とも数値rankのある行の後に置く。この並べ替えはQuest masterの要求値を対象とし、
プロフィールの習得スキルや受注可否は判定しない。

### 発見物

- 発見物分類
- 未発見
- 発見済み・未報告
- 報告済み
- カード所有／非所有

一覧は主要列で並べ替え可能とする。

マスターデータ画面の下部には、データ提供元である「大航海時代データベース」と
データを収集・整理・更新・公開してきたコミュニティへの謝辞を表示する。
外部サイトはユーザー操作時のみ既定ブラウザーで開く。この謝辞は公式・公認・提携・保証を意味しない。

## 5.9 達成度の可視化

選択中プロフィールについて、少なくとも以下を表示する。

- 発見物総数
- 発見済み数
- 通常発見物（レリックを除く）の発見率
- 発見物分類ごとの総数
- 発見物分類ごとの発見済み数
- 発見物分類ごとの達成率
- 未報告発見物数
- 発見済み発見物のうちカード所有数
- 発見済み発見物のうちカード所有率
- プロフィールごとの報告履歴・旧算入資格・特殊自動報告から算出した冒険勲功値（判明分）

クエストについても、全体の総数・達成数・達成率を表示可能な設計とする。

概要の対応するカード見出しは「クエスト」「発見物」とし、進捗バーのアクセシブル名にも同じ名称を使う。
主要な進捗は「クエスト」「発見物」、補助的な進捗は「冒険勲功値」「現在未報告」「カード所有」の順とする。
広い画面では主要2列・補助3列、中間幅では両グループを2列（補助の最後は1列分の幅）、狭い画面では各1列で表示する。

「発見物」カードの主表示は「発見済み」とし、レリック分類を除く発見済み数／総数・達成率・進捗バーを表示する。
通常発見物の総数・発見済み数は、既存の全発見物集計から種別名が`レリック`に完全一致する分類別集計を差し引く。
オファー方法では判定せず、トレジャーハント由来の史跡・歴史遺物も通常発見物に含める。
同じカード内の補助表示に「レリック」としてレリック分類の発見済み数／総数、「総発見数」としてレリックを含む全発見済み数／全総数を添える。画面上には集計範囲の説明や参考値などの補足を付けない。
全体・分類別とも既存のactiveマスター集計を再利用し、レリック分類がない場合は0件、主表示の分母が0件なら達成率は0%とする。
カード所有の分母・所有率、未報告・冒険勲功値、分類別表示・遷移は変更しない。

集計結果は原則としてSQLiteクエリで算出し、v1では集計専用の永続テーブルを持たない。

概要の発見物分類別カードは、category IDで指定した発見物一覧への移動入口とする。
移動時は発見物一覧の検索・状態・カード所有filterを既定値へ戻し、指定分類だけを適用して
1ページ目から表示する。現在選択中のプロフィールは維持し、存在しない分類IDは「すべて」へ戻す。
移動指定は一度だけ適用する一時的なUI stateとし、永続化しない。

概要の「現在未報告」カードからは、状態filterを「発見済み・未報告」にして発見物一覧へ移動する。
既存の有効な報告状態で絞り込み、自動報告済み・報告対象外のレリックを含めない。
概要の「カード所有」カードからは、カード所有filterを「未所有（発見済みのみ）」にして移動する。
未発見とカード対象外のレリックは含めず、概要の所有数・所有率は変更しない。
両カードに一覧表示の操作案内文は付けず、移動ボタンのアクセシブル名とキーボード操作・フォーカス表示は維持する。未所有件数は概要のカード対象発見済み数から所有数を引いた値と一致する。

分類・未報告・カード未所有の移動指定は区別し、指定したfilter以外は既定値、ページ番号は先頭にする。
各カードの移動操作にはbuttonを使い、マウスとEnter／Spaceで操作できる。0件でも操作を無効にしない。
移動後のfilterは自由に変更でき、指定を再適用しない。通常のサイドバー移動では指定を引き継がない。
プロフィール変更時も移動指定を再適用せず、一覧は従来どおりfilterを初期化して選択中プロフィールの進捗を表示する。

達成率・発見率および分類別達成度は、原則として `is_active = 1` の現在有効な
マスターだけを分母・分子の対象とする。非アクティブなマスターに紐づく既存進捗は
保持するが、現在の集計には含めない。

冒険勲功値はプロフィール別に、初回報告確認済み、旧参考値の引継ぎ資格あり、現在発見済みかつ特殊自動報告対象、の発見物IDの和集合から算出する。同じ発見物は一度だけ数え、レリックを除外し、非active発見物も含める。経験値NULLは合計に加えず、不明件数に含める。現在の未報告・報告済み件数は従来の有効報告状態で集計する。
`experience = NULL`は合計に含めず、UIの見出しは「冒険勲功値」とし、判明している経験値だけを使った参考値であることの説明をカード内に維持する。爵位thresholdや
爵位判定はこの機能の対象外とする。

## 5.10 マスターデータの手動インポート

ユーザーはローカルファイルから、以下のGVDB公開データを明示的にインポートできる。

- `quests.csv`
- `discovery_items.csv`

GUI上で対象datasetのローカルファイルを選択し、内容の解析結果を確認した後、明示的な
インポート操作によってのみマスターデータを更新する。

クエスト・発見物画面のマスターデータ未登録時には、取り込み先を説明し、「マスターデータを開く」ボタンから既存のマスターデータ画面へ移動できるようにする。検索・絞り込み後の0件とは区別し、プロフィール未選択、読み込み中、エラーの既存表示は維持する。

マスターデータが0件でも、進捗取得に失敗した場合は取得エラーを優先し、取り込み案内を同時に表示しない。
発見物のマスターデータは存在するが有効な発見物が0件の場合は、その状態と登録状況の確認先を案内する。検索・絞り込み条件の変更は促さない。

## 5.11 バックアップと復元

ユーザーはGUIからSQLiteデータベース全体の整合したバックアップをローカルファイルへ
手動保存できる。バックアップにはマスターデータ、プロフィール、クエスト進捗、発見物進捗、
インポート履歴を含む現在のDB全内容を含める。

ユーザーは検証済みバックアップを選択し、現在のDBがバックアップ時点へ置き換わる旨を
確認した後にのみ復元を実行できる。復元後はアプリケーションを再起動する。

バックアップ作成は現在DBを変更してはならない。復元対象は現在DBを変更する前に整合性、
必須schema、migration互換性を検証し、復元失敗時は操作前のDBを維持する。自動、定期、
クラウド、ネットワーク経由のバックアップはv1では実装しない。詳細な安全規則は
`backup-restore.md`を正本とする。

アプリケーション自身がGVDBから自動ダウンロードしてはならない。

インポート仕様の詳細は `data-import.md` を参照する。

## 5.12 データ保存場所

標準保存場所は実行ファイルdirectoryを基点とする`data/dol-progress.db`、bootstrapは同じ基点の`config/data-root.json`と`config/data-root.last-good.json`とする。Rustの`PortablePaths`で一度解決し、Current Working Directoryに依存させない。旧AppDataのDB/bootstrapは探索・自動移行せず、AppDataへの自動fallbackも行わない。

初回の標準DB初期化成功後はcommitted Default locatorを保存する。両bootstrapがない既存portable DBは検証後に採用し、設定が残っているのにDBが欠落した場合は空DBを作らずRecoveryとする。configと、Default使用時のdataの書込み不能・directory名のfile衝突は、WebView生成前のnative errorと終了で扱う。

ユーザーは設定画面から、従来と同じローカル固定NTFS上の外部空directoryへDB全体を安全に移行できる。実行ファイルdirectory、その子directory、親directoryをCustom rootとして選択できない。移行は整合したsnapshotを使用し、旧DBを削除しない。Custom rootが使えない場合はRecoveryとし、inactiveな標準DBを開いたりdata directoryを自動作成したりしない。詳細は`data-root.md`を正本とする。

このportable保存方式の対象はアプリ所有のDB/configである。異なるEXEフォルダーは別々のDefault DBを使用する。WebView2のuser-data/cacheは現行TauriのLocalAppData default（Option A）を維持する。同じWindowsユーザーの異なるEXEコピーはWebView2 UDFを共有し、複数フォルダーからの同時起動は現時点の保証対象としない。Runtime事前検査は3.3に従う。

保存場所画面は「データベース」と「アプリの設定」を別cardに分ける。前者はRustのdataRootを「データベースのフォルダー」として表示し、「データベースの保存場所を変更」操作を置く。Customの場合だけ同cardに「カスタム保存先を使用しています」と補足する。後者はconfigRootを「設定フォルダー」として表示し、「設定フォルダーにはアプリの設定が保存されます。」と説明する。設定はDB移行の対象ではなく、同cardに変更操作を置かない。通常表示にDB file path、アプリfolder、保存方式や標準data folderを並べない。表示用pathはRustからread-only情報として取得し、Frontendでは組み立てない。移行先の条件は固定NTFS等のbackend検証に合わせて箇条書きで示す。画面内の案内はbackup操作の場所、起動中の手作業移動・手編集を避けること、終了後のEXE削除、DB/設定削除前のbackup確認、WebView2使用の説明に絞る。folder copy、更新、標準/Customの違い等の詳細はREADMEに記載する。

DB backup・ファイルの手動移動/編集・アプリ削除の案内は「データとアプリの管理」cardにまとめ、WebView2の補足情報は「Windows側に残るデータ」cardに分ける。

Recovery画面は既存DBの再指定等の復旧操作を維持する。画面reloadだけを「再試行」と表示せず、保存場所を修正した後はアプリの終了・再起動を案内する。新しいrestart機構や空DB作成操作は追加しない。

## 5.13 実行中バージョンの表示（Map-C12B）

ステータスバーに「進捗データはローカルに保存されます」と表示し、右側に実行中アプリのバージョンを`v0.3.0`形式で控えめに表示する。
番号はReactコードへ固定せず、Tauri 2の`@tauri-apps/api/app`の`getVersion()`で取得する。表示機能自体はアプリバージョンを書き換えない。正式版の番号はRelease準備で整合させ、Map-C12Fでは`0.4.0`とする。
既存の`core:default`に含まれる権限を使用し、取得のための権限や依存を追加しない。

バージョンは画面描画を待たせず非同期で取得し、通常の画面切替では再取得しない。
React StrictModeのeffect再実行でも同じ取得Promiseを使用し、アンマウント後は結果をstateへ反映しない。
取得中・取得失敗・Tauri APIが利用できないブラウザ環境ではバージョンを省略し、通常画面と保存先の文言を表示する。
取得失敗をアプリ全体のエラーにせず、自動再試行やダイアログを追加しない。

狭い幅ではフッター内を折り返せるようにし、バージョン文字列は分割せず右寄せする。
Map-C12C-Bではバージョンを情報表示のボタンとし、非モーダルのアプリケーション情報を開けるようにする。
開くだけでは通信せず、利用者が「更新を確認」を押した場合だけ、固定のGitHub Releases latest APIへGETする。
この明示操作による公開Releaseの確認だけをオフライン原則の限定的な例外とする。通常機能はオフラインで使用できる。

確認先は`https://api.github.com/repos/guardiancrow/dol-progress/releases/latest`に限定し、credentialsを省略、referrerを送らず、redirectを拒否する。
10秒の全体timeout、JSON body最大1MiB、assets最大256件を設け、通常は60秒間隔で確認する。制限応答で判明した待機期限はそれ以上待つ。
起動、StrictModeのeffect、パネルの開閉、画面切替では更新確認を開始しない。連打を抑止し、AppShell破棄時は中断して古い応答を反映しない。
個人・プロフィール・進捗データ、認証token、Cookieを要求に付加しない。IP等の通常の通信メタデータが伝わり得ることを表示する。

対象はGitHubのLatest指定通常公開版一つであり、全Release中の最大SemVerを保証しない。
通常の3整数のバージョンを数値比較し、tagの先頭小文字vを許可する。prerelease、metadata、不正形式は比較不能とし補完しない。
新版として案内するには、既存の命名規則によるWindows x64ポータブルZIPと外部SHA-256 assetが一意に存在し、uploaded状態で有効なsizeであることを確認する。
未確認、確認中、新版あり、同じ版、現在版が新しい、対象配布物未確認、比較不能、通信失敗を区別する。新版かつ配布物確認済みの場合だけフッターに「更新あり」を添える。
Release本文・画像・Markdown・任意URLは描画・実行せず、配布物を掲載しているという確認を内容の安全性検証やhash照合と混同しない。

別の明示操作から固定の`https://github.com/guardiancrow/dol-progress/releases`を既定ブラウザーで開ける。API応答のリンクは使用しない。
パネルはEscapeと外側操作で閉じられ、Tabを閉じ込めない。取得失敗は通常利用やナビゲーションを妨げず、最新版へ読み替えない。
結果と待機期限はメモリーだけに保持し、永続キャッシュ・通知設定を追加しない。
自動通信、自動ダウンロード、自動インストール、GVDBの自動取得・書込み、進捗データの外部送信は行わない。
データ保存場所・起動・同意処理、DB schema・migration、配布形式とバージョン番号は変更しない。

## 6. 状態遷移

## 6.1 クエスト

```text
未達成
  │ 達成として登録
  ▼
達成済み
  │ 未達成へ戻す
  ▼
未達成
```

DB表現:

```text
未達成   = quest_progress 行なし
達成済み = quest_progress 行あり
```

## 6.2 発見物

以下は手動報告を行う通常発見物の遷移である。特殊クエストの非レリックは登録時に報告済みとなり、唯一のactive関連Questから自動報告状態を導出できる場合は手動で未報告へ戻せない。レリックは発見済みを最終状態とし、報告操作は対象外とする。

```text
未発見
  │ 発見として登録
  ▼
発見済み・未報告
  │ 報告済みに変更
  ▼
報告済み
```

報告済みから未報告へ戻す操作も可能とする。

発見済みを未発見へ戻す場合は `discovery_progress` 行を削除する。

## 6.3 カード

```text
所有 <-> 非所有
```

カード状態は発見物が発見済みである間だけ管理する。

## 7. データ保護要件

以下は必須要件とする。

1. マスター更新でプロフィールを削除しない。
2. マスター更新でクエスト進捗を削除しない。
3. マスター更新で発見物進捗を削除しない。
4. GVDB側のマスターからレコードが消えても、ローカルでは物理削除せず非アクティブ化する。
5. マスター更新失敗時は途中状態を残さない。
6. データベースファイルをコピーすることで、ユーザーデータをバックアップできる構造とする。

## 8. 非機能要件

### 8.1 オフライン動作

通常利用は完全にオフラインで動作すること。5.13の利用者による手動更新確認だけを限定的な例外とし、通信不能でも基本機能を使用できること。

### 8.2 性能

数千〜数万件規模のマスターを想定する。

通常の一覧、絞り込み、検索、進捗更新がローカルPC上で十分な応答速度を持つこと。

v1では過剰なキャッシュや検索エンジンを導入しない。

### 8.3 信頼性

- SQLiteの外部キー制約を有効にする。
- 複数テーブルにまたがるマスター更新はトランザクションを使用する。
- 外部ファイルは検証後にDBへ反映する。
- 不正な入力を理由に既存ユーザーデータを変更しない。

### 8.4 保守性

- DB変更はmigrationで管理する。
- UIとSQLを分離する。
- マスター取込処理を独立したモジュールとして実装する。
- 仕様変更時は対応するドキュメントも更新する。

### 8.5 初回起動時の使用許諾確認

承認済みの使用許諾本文・条件versionを組み込んだ後、Runtime preflightとPortablePaths取得の後、通常のconfig／data準備・Tauri起動・DB初期化の前に同意設定を確認する。

- 記録がなければ既存のNative画面を表示し、「同意する」を選択して保存できた場合に起動する。
- 「同意しない」、Esc、画面を閉じる操作では通常起動を中止する。
- 同じ本文・versionへの同意記録が有効なら、次回以降の画面を省略する。
- 記録はEXE親のconfig/consent.jsonへ保存する。custom DBへ移動しない。
- 古い条件・本文不一致では再確認する。破損・未対応の記録、読取り・保存・表示の失敗は起動を止め、既存記録を勝手に削除・修復しない。
- 記録は再表示判定の設定であり、本人認証や法的な同意立証のための監査記録ではない。
- 起動時のleaseはNormal／Recoveryの状態登録まで保持して解放し、アプリの稼働中に保持し続けない。新たな多重起動防止機能にはしない。

### Map-C5R-S：地図発見物に限定した操作（旧仕様）

この節はUI-R2B以前の地図限定UIを記録する。現在有効なUI範囲と確認手順は、次節「UI-R2B：初回報告履歴UIの共通化」に従う。

U1〜U3で追加した初回報告UIは、既存のmapRelated判定により対象地図との関連が確認できる発見物だけに限定する。レリック・自動報告対象には提供しない。非対象行は初回報告欄を控えめな—とし、不明表示・チェック・履歴確認ボタンを表示しない。列名は「地図の初回報告」とし、ヘッダーのtooltipは「地図から発見できる発見物について、過去に一度でも報告したかを示します。地図以外の発見物は対象外です。」とする。チェック・確認ボタンのアクセシブル名にも「地図の初回報告」を用いる。列幅は7remとし、既存の44px行高を維持する。地図以外の従来の発見・報告・カード・メモ操作と内部履歴管理は変更しない。

地図対象では現在状態の3状態selectと初回報告チェックを独立して操作する。チェック変更では希望値を示す1つの確認画面から保存する。不明・矛盾状態は同じ画面内の2択（初回報告済み／初回報告前）から明示的に選んで保存する。初回報告前への訂正は過去の実績を取り消す操作であり、通常の再発見で履歴を消さないことを説明する。冒険勲功値・算入対象への影響はその場に表示する。通常UIからunknownへの戻しやlegacy資格だけの訂正は提供しないが、内部の訂正APIとテストは保持する。

現在報告済みを初回報告前へ訂正する場合だけ、現在状態も未報告または未発見へ訂正する方法を明示選択させる。未発見を選んだ場合のカード・メモ等の削除も同じ画面で説明する。同時訂正は既存correctHistoryの単一transactionを使い、追加の確認画面へ進ませない。保存中は操作を無効化し、キャンセルでは無変更、競合・保存結果不明では最新状態を取得する。操作直前には最新snapshotのactiveな地図関連も照合する。複数地図に紐づいていても同じプロフィール＋発見物IDを更新する。

このPhaseでは概要の「現在未報告」の総数を維持し、初回報告前／初回報告済み／履歴未確認の内訳表示を撤去した。後続Map-C7では集計を変更せず、以下の名称と説明で内訳を表示する。冒険勲功値・その他の進捗集計は維持する。クエスト一覧への追加UIはなく、達成・地図の状態・地図の入手filterを変更しない。

### UI-R2B：初回報告履歴UIの共通化

発見物一覧の列名を「初回報告」とし、activeな通常発見物では地図の有無にかかわらず確認・訂正できる。レリック・特殊自動報告対象には操作を提供しない。非active発見物は従来どおり通常一覧に表示しない。既存のcheckboxと小さな確認ボタンを使い、新しい列や毎行の追加ボタンを設けない。列幅7rem・行高44pxを維持する。ヘルプとアクセシブル名を共通化し、現在の報告状態と過去の初回報告実績が別の記録であることを説明する。

新規の発見済み・未報告登録から初回報告前と推定せず、履歴行なしはunknownとして扱う。未確認履歴は、現在報告済みによるチェック表示の補完がある場合も、確認フォームを未選択で開く。利用者が初回報告前または初回報告済みを選び、明示的に保存する。既存のconfirmed・not_reportedではcheckboxの希望値をフォームの初期選択に使う。キャンセルや表示だけでは保存しない。

初回報告前を選んだ場合、未確認履歴には「初回報告をまだ行っていないことを記録します」と説明し、confirmedからの訂正には過去の報告実績を取り消すことを明示する。旧算入資格がある場合は、その解除と既存の勲功値・算入対象・経験値不明件数への影響を示す。現在報告済みとの矛盾がある場合は、未報告または未発見への同時訂正を明示選択させる。未発見への訂正ではカード・メモ等の削除範囲を説明する。

編集対象は一覧summaryと最新snapshotの両方でactive・非レリック・非自動報告を確認する。プロフィール・発見物IDと状態を照合し、地図関連の有無が食い違う場合も再取得して操作を止める。地図行はactiveな対象地図との関連確認を維持し、非地図行には地図関連を要求しない。履歴取得に失敗している間は操作できない。

保存は既存correctHistoryとsourceMapId=nullを使い、現在進捗の同時訂正も既存の単一transactionで行う。プロフィール切替時の確認破棄・旧応答の無視、競合・保存失敗時の再取得、二重送信の抑止を維持する。閉じた後は保存・再取得の完了を待ち、可能なら同じ行の操作へフォーカスを戻す。履歴の自動修復・一括変換、DB schema・migration・勲功値の算入規則・通常の報告状態遷移は変更しない。概要・分類別内訳と一覧filterは保存後の履歴を従来の条件で反映する。

### UI-R2C：初回報告の確認結果を不明に戻す

既存の履歴訂正フォームで「不明」「初回報告前」「初回報告済み」を選べる。checkboxから開いた場合も選択欄を表示し、従来の希望状態を初期選択にする。未確認履歴では未選択で開き、履歴行なしと明示unknownは同じ未確認状態として扱う。同じ履歴の選択では保存を無効にする。行内の列・操作数、7rem列幅・44px行高、キーボード操作とフォーカス復元を維持する。

現在が未報告または未発見なら、not_reported・confirmedからunknownへの明示訂正を許可する。確認結果を撤回する操作であり、現在進捗・カード所有・メモ・クエスト達成は変更しない。現在進捗を削除しても履歴を保持する従来契約と、履歴を不明へ戻す操作を区別して説明する。

現在報告済みの場合はunknownへの訂正を許可せず、理由を表示して保存を無効にする。現在報告済みの補完表示と履歴保存値の食い違いを避けるためである。unknownと現在状態の同時訂正は提供しない。not_reportedと現在報告済みの矛盾には、従来の未報告・未発見への同時訂正を維持する。

unknownの保存は既存correctHistoryへstatus=unknown、removeLegacyCredit=false、currentState=null、sourceMapId=nullを渡す。履歴行を削除せず、unknownとして保存する。旧算入資格を新設・復元せず、既存のunknownに旧資格が残る場合だけ既存APIの保持規則に従う。confirmedからの訂正で失われる勲功値・算入件数を表示し、経験値NULLなら経験値不明件数への影響を示す。履歴・集計情報を確認できない場合や許可されない選択では、影響額・件数を確定表示しない。

保存直前に最新snapshotを再取得し、確認画面を開いた時点のsnapshot全体と比較する。進捗・履歴・マスター・関連クエスト等が変わっていた場合は保存せず再取得する。active・非レリック・非特殊自動報告の対象条件を維持し、地図関連の変更も検知する。Rust側も従来どおり単一transaction内でexpectedを照合する。プロフィール切替、二重送信の抑止、失敗・競合時の再取得を維持する。Rust保存API・勲功値算入SQL・DB schema・migrationは変更しない。

## Map-C7：概要の現在未報告の内訳

概要の「現在未報告」は、選択中プロフィールの進捗行が存在し、有効な現在報告状態が未報告である、
activeな非レリック発見物を対象とする。地図だけに限定せず、分類未登録の発見物も既存条件に従って含める。
特殊な自動報告で有効報告済みとなる発見物は、保存値が`reported=0`でも含めない。
初回報告履歴は`profile_id`と`discovery_id`でLEFT JOINし、履歴行がない場合はunknownとして分類する。

同じ母集団を既存の`unreportedBreakdown`で次の3区分へ分類し、同一のカード内へ表示する。

| 表示名 | 初回報告履歴 | 意味 |
| --- | --- | --- |
| 初回未報告 | `not_reported` | 初回報告をまだ行っていない発見物 |
| 再報告待ち | `confirmed` | 初回報告済みで、現在は再発見後の未報告状態にある発見物 |
| 履歴未確定 | `unknown`または履歴行なし | 初回・再報告のどちらかを確定できない発見物 |

現在未報告＝初回未報告＋再報告待ち＋履歴未確定とする。重複する地図Questがあっても発見物を一度だけ数える。
再発見や現在進捗の変更によってconfirmedの履歴を変更せず、再発見は再報告待ちへ分類する。
`unknown + legacy_merit_credit=1`も履歴未確定とし、初回報告済みへ読み替えない。
legacy算入資格、特殊自動報告、経験値の判明状態と初回報告履歴の区分は独立して扱う。
初回未報告件数を獲得可能勲功値や勲功値未算入の件数として表示しない。

初回未報告と再報告待ちは0件でも表示し、履歴未確定は1件以上のときだけ表示する。
短い説明と意味のあるラベルを付け、既存の総数・一覧への遷移・カード順・主要2列／補助3列の配置を維持する。
内訳が未取得・不正、または合計が総数と一致しない場合は推測で補完せず、総数と「未報告の内訳を確認できません。」を表示する。
冒険勲功値カードの内容と計算、その他の概要集計、地図の初回報告UI、履歴保存・訂正、SQL・DB schemaは変更しない。

## Map-C8：発見物分類別の現在未報告内訳

概要の既存の発見物分類別カードにも、Map-C7と同じ初回未報告・再報告待ち・履歴未確定を表示する。
activeな発見物を`category_id`でまとめる既存SQLの3区分を、そのまま分類別の行モデルへ渡す。
現在未報告の条件と履歴JOINは概要総数と共通であり、レリック、特殊自動報告、unknown＋legacyもMap-C7と同じ契約で扱う。
同じ発見物は一つの分類だけに属し、複数Questが関連していても重複して数えない。
各分類で、現在未報告＝初回未報告＋再報告待ち＋履歴未確定とする。

分類NULLは従来どおり概要総数に含めるが、分類別カードには追加しない。
既存SQLは分類別の最終出力で分類マスターへINNER JOINしており、分類NULLの表示行は返さないためである。
この場合、概要総数と表示された分類別件数の合計との差は分類NULLの分であり、新しい「未分類」カードを追加して埋め合わせない。
有効な発見物がない分類も引き続き表示しない。分類順、総数・発見済み・達成率・未発見・未報告・カード所有の既存表示を維持する。

画面は表へ変更せず、2列の分類別カードの既存数値の下に小さな内訳行を加える。
初回未報告は0件でも表示し、再報告待ちは原則として0件でも表示する。履歴未確定は1件以上のときだけ表示する。
Owner確定のゲーム仕様に従い、分類別カードの「港・集落」「伝承」に限り再報告待ちが0件なら項目を省略する。
この2分類で1件以上ある場合は、件数を保持して「再報告待ち（要確認）」と表示し、再報告の概念がない分類のため現在状態と初回報告履歴の確認が必要であることを説明する。
分類の識別は、既存の分類マスター名の完全一致で行う。ローカル採番の分類IDを固定値にせず、部分一致や地図の有無から判定しない。
「気象・現象」は地図の有無と関係なく再報告可能な通常分類として扱い、0件・1件以上とも従来の表示を維持する。
この例外は分類別だけに適用し、Map-C7の概要カード、SQL、総数、3区分の集計値、勲功値は変更しない。
レリックは「報告: 対象外」を維持し、内訳と内訳の確認メッセージを表示しない。
値が未取得・不正、または内訳の和が従来の現在未報告と異なる場合は、従来の総数を残し、
「未報告の内訳を確認できません。」と表示する。差分を推測で他の区分へ加えない。
表示部品と検証規則はMap-C7と共通にし、分類名を含むアクセシブルな内訳ラベルを付ける。
既存の分類別一覧への移動、キーボード操作、概要カードと冒険勲功値の内容を維持する。
SQL、クエリ回数、保存データ、schema、初回報告操作は変更しない。

## Map-C12A：発見物一覧の未報告内訳と地図の判定保留

発見物一覧の「状態」の直後に「未報告の内訳」filterを置く。選択肢は「すべて」「初回未報告」「再報告待ち」「履歴未確定」とする。
Map-C7/C8と同じ現在未報告の集合を対象に、保存履歴の`not_reported`、`confirmed`、`unknown`または履歴行なしで分類する。
地図以外や分類未設定の発見物も対象とし、レリックと有効報告済みの特殊自動報告は除外する。
旧算入資格、維持意思、現在の進捗だけから履歴を推測しない。`unknown + legacy_merit_credit=1`は履歴未確定のままとする。

内訳filterは状態filterとAND条件で併用する。状態が「すべて」でも各内訳は現在未報告だけを抽出し、状態が「未発見」「報告済み」なら一致する行はない。
「すべて」は内訳条件だけを解除する。分類・カード・地図・検索とのAND条件とソートを維持し、filter変更時は先頭ページへ戻す。
一覧の件数とページ数は全条件適用後の集合から算出する。概要からの移動では内訳を「すべて」で開始する。

履歴は既存のプロフィール単位の一括取得を使い、行ごとの取得を追加しない。取得中と取得失敗は、取得済みで履歴行がない場合と区別する。
内訳選択中の取得待ち・失敗では結果件数・空一覧・ページ数を確定表示せず、読込中または取得できない旨を表示する。
再取得中も旧履歴で内訳を確定せず、失敗後は再読み込みできるようにする。プロフィール切替後に旧プロフィールの遅延応答を反映しない。

発見物一覧の「地図・要確認」は、filterと名称付近の表示をともに「地図・判定保留」へ改称する。
名称付近の表示にマウスを重ねるかキーボードでフォーカスすると、その行に当てはまる次の理由を表示する。両方に該当する場合は両方を表示する。

- 一つの地図に複数の発見物が関連しているため、再入手の判定を保留している。
- 報告対象外の発見物であるため、再入手の判定を保留している。

対象地図は既存のactiveな7分類地図とし、関連件数の確認には非active発見物との関連も含める既存SQLを維持する。
判定保留は地図の再入手に関する分類であり、初回報告履歴の「履歴未確定」とは独立して扱う。
再入手候補・抑止の条件、概要の総数・内訳・勲功値、状態遷移・履歴訂正、保存データ、schema・migrationは変更しない。

## UI-R3B：コンパクトレイアウトと手動開閉

初期ウィンドウサイズ800×600を維持する。自動表示はCSS表示領域の幅・高さで判定し、物理解像度を直接使用しない。幅56rem以下ではメニューを閉じる。幅56rem以下または高さ50rem以下ではクエスト・発見物の詳細フィルターを閉じ、それ以外は詳細フィルターを展開する。ヘッダーはUI-R3Eに従う。

メニューは「自動／手動で展開／手動で折りたたみ」の3状態を持ち、起動時は自動とする。開閉ボタンは常に利用でき、画面サイズに関係なく手動で変更できる。手動選択はリサイズで上書きせず、画面を移動してもアプリ起動中は保持する。DB・設定ファイルへは保存しない。ヘッダーの自動・手動開閉はUI-R3Eで撤去する。

アプリ名と現在のプロフィールを常時確認できるようにする。プロフィール選択の配置はUI-R3Dに従う。メニューは非モーダルのインライン表示とし、閉じるとメイン領域へ幅を返す。既存6画面への移動、現在ページの識別、フッターのバージョン表示を維持する。

クエスト・発見物一覧の通常表示は検索欄、詳細フィルター開閉ボタン、適用条件の表示、一覧件数、テーブル、ページ送り・件数変更を残す。テーブル優先表示はUI-R3Eに従う。検索以外の条件と地図・前提クエストのヘルプは詳細領域へまとめる。条件数は検索を除く有効なcolumnFiltersから算出し、検索中・並べ替えありは別に表示する。要求Rankの並べ替えを条件数へ加算しない。

詳細フィルターの手動選択は一覧コンポーネントの表示中に保持する。開閉・リサイズでテーブルを再マウントせず、検索・条件・並べ替え・ページ番号・ページサイズを変更しない。実際の条件変更やプロフィール切替、画面移動に伴う既存の初期化契約は維持する。閉じた条件も適用し続ける。開いた詳細領域は高さを制限して内部スクロールを可能にし、テーブルを押し出し続けない。

テーブルは縦横スクロールと固定見出しを維持し、ページ操作はテーブルのスクロール領域の外に置く。列・列幅・44px通常行高は変更しない。800×600の自動状態で、通常行3行以上と見出し、ページ操作を初期表示から利用できることを目標とする。600×480も追加検証し、さらに小さい表示領域、文字拡大、長文行、多数のエラー等で収まらない場合はメイン領域のスクロールで操作可能にする。

開閉ボタンにaria-expandedとaria-controlsを付ける。閉じた領域をTab移動・読み上げから除外し、内部にフォーカスがある場合は自動折りたたみでも先に開閉ボタンへ移す。新たなEscapeの全体処理やフォーカストラップは追加しない。レイアウト変更で進捗操作・DB書き込みを発火せず、保存中や確認中のダイアログを破棄しない。初回報告履歴・地図状態・関連情報(i)・エラー通知・プロフィール切替の既存契約を維持する。

寸法はjsdomの構造テストと区別してブラウザーの合成データで測定し、Tauri実ウィンドウやOSの表示倍率での確認と混同しない。保存API・集計・スキーマ・依存関係・バージョンは変更しない。

## UI-R3D：プロフィール選択のヘッダー統合

既存ProfileSelectorをサイドメニューからヘッダー右側へ移す。現在のプロフィール名はselectの選択値で表示し、独立した名前のテキストを重ねて表示しない。選択欄は一つだけ生成し、開閉・リサイズでも再マウントしない。プロフィール一覧・選択状態・切替処理には既存ProfileContextを使う。

ヘッダー左側の操作ボタンはUI-R3Eに従い、右側のプロフィール選択と視覚的に分ける。選択欄はメニュー・一覧表示モードにかかわらず利用できる。表示ラベルを読み上げ用に残し、アクセシブル名「現在のプロフィール」とselectのキーボード操作を維持する。

選択欄の幅を画面に合わせて制限し、長い名前でヘッダー全体を押し広げない。optionには名前を省略せず保持し、選択欄のtitleでも現在の名前を確認できるようにする。読込中・プロフィールなしの無効化は従来どおりとする。800×600では約56pxのコンパクトヘッダー、通常行4行程度、検索・ページ操作へのアクセスを維持する。600×480も追加検証する。

UI-R3Bの自動判定・手動優先、UI-R3CのSVG・操作領域・フォーカス表示は維持する。プロフィール変更後の進捗読取と表示更新、保存・集計・プロフィール管理の業務ロジックは変更しない。

## UI-R3E：常時コンパクトヘッダーとテーブル優先表示

ヘッダーは全画面で約56pxとし、補足表示とヘッダー専用の展開状態を撤去する。アプリ名、メニュー開閉、プロフィール選択は常時利用できる。クエスト・発見物画面だけ、アプリ名の横に40px程度のSVGボタンを置く。表示中は「検索・フィルターを隠す」、非表示時は「検索・フィルターを表示」とし、aria-label・title・aria-expandedを同期する。操作領域が存在する場合はaria-controlsで関連付け、読込中等で領域が存在しない間は操作を無効にする。

初期状態は通常表示とし、検索欄とUI-R3Dの800×600での通常行4行程度を維持する。テーブル優先表示は手動で選び、クエスト・発見物ごとにAppShellの生存中だけ保持する。リサイズで上書きせず、DB・設定ファイルへ保存しない。画面を戻ったときの表示モードだけを保持し、画面移動やプロフィール変更に伴う検索・進捗等の初期化契約は拡張しない。

テーブル優先表示ではページ見出しの視覚的な表示と余白、検索欄、詳細フィルターとその開閉ボタン、件数サマリーを隠す。ページ見出しの読み上げ上の意味は残し、ヘッダーに現在の画面名を表示する。検索・詳細条件・並べ替えが適用中なら、その事実を区別して簡潔に表示する。条件数に検索や要求Rankの並べ替えを二重計上しない。

検索欄・詳細フィルターはDOMに保持する。表示切替だけで検索文字列、条件、詳細領域の開閉状態、並べ替え、ページ位置・件数を変更せず、テーブルを再マウントしない。ページ送り・件数変更、保存中・エラー等の通知、履歴訂正・地図状態・進捗操作は引き続き利用できる。表示切替によるDB書き込みを行わない。

検索・フィルター内にフォーカスがある場合は、先にヘッダーの開閉ボタンへ移す。テーブル内のフォーカスは不必要に変更せず、隠した操作要素をTab移動から除外する。確認ダイアログを破棄しない。関連情報(i)も表示切替では閉じず、アンカーの位置を再測定する。既存のEscape操作と、その他の外側クリックによる終了は維持する。スクロール位置は明示的にリセットしないが、表示領域が広がって末尾を超える場合はブラウザーによる上限補正を許容する。

800×600、1024×768、1280×720、1920×1080、追加で600×480を合成データで測定する。テーブル優先表示で可視領域が増え、ページ操作へアクセスできることを確認する。長文・長いプロフィール名・エラー・条件適用中も確認する。保存API・集計・列幅・44px通常行高・バージョン・初期ウィンドウサイズは変更しない。
