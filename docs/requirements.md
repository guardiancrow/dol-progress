# 要件定義

## 1. 文書の目的

本書は、「大航海時代 Online」のクエストおよび発見物の進捗をローカルで管理する
デスクトップアプリケーションの機能要件と非機能要件を定義する。

DBの具体的な列定義は `database-design.md`、GVDB公開データの取り込み方法は
`data-import.md` を正とする。

## 2. 背景

「大航海時代データベース（GVDB）」には、クエスト情報や発見物情報など有用な
マスターデータが公開されている。

一方、キャラクターごとのクエスト達成状況や発見物の進捗は、長期間にわたって
自分自身で保持したい情報である。

本アプリケーションは、GVDBの公開マスターデータをローカルへ取り込み、
ユーザー固有の進捗情報はローカルSQLiteへ永続保存することで、この用途を実現する。

本アプリケーションはGVDBの代替サイトを目的としない。また、GVDBへの書き込みや
不要なアクセスを行わない。

## 3. 対象環境

### 3.1 初期ターゲット

- Windowsデスクトップ
- 単一ユーザー
- ローカル利用

### 3.2 通常利用時の前提

- インターネット接続を必要としない。
- SQLiteデータベースはユーザーPC上に保存する。
- GVDBマスターの更新は、ユーザーが手動で取得したファイルを明示的にインポートする。

## 4. ドメイン用語

### 4.1 プロフィール

本アプリケーションにおける「プロフィール」は、ゲーム内の1キャラクターを表す。

1つのアカウントに複数キャラクターが存在する場合でも、進捗はキャラクター単位で
独立して管理する。

v1ではゲームアカウントそのものを別エンティティとして管理しない。

### 4.2 クエスト

GVDBの `quests.csv` に含まれる1レコードを、本アプリケーション上のクエスト系
マスターとして扱う。

GVDB上で「地図」等として扱われるレコードも、`quests.csv` に含まれる限り
同一のマスター集合として管理する。

### 4.3 発見物

ゲーム内の発見物を表す。

発見物には少なくとも次の状態が存在する。

- 未発見
- 発見済み・未報告
- 報告済み

### 4.4 発見物カード

発見物に付随するカードの現在の所有状態を表す。

カード所有状態は、発見済み／報告済みと独立して管理する。

カードは失う場合があり、再取得する場合もある。

v1ではカードの取得・消失履歴そのものは管理しない。

### 4.5 マスターデータ

GVDB公開データから取得・更新される情報。

主な対象:

- クエスト
- 発見物
- 発見物分類
- クエストと発見物の関連
- クエスト前提関係
- クエスト必要スキル
- クエストの個別オファー都市

### 4.6 ユーザーデータ

ユーザーが本アプリケーション上で作成・更新する情報。

対象:

- プロフィール
- キャラクター別クエスト進捗
- キャラクター別発見物進捗
- 報告状態
- カード所有状態
- ユーザー入力メモ

マスターデータ更新によってユーザーデータを失ってはならない。

## 5. 機能要件

## 5.1 プロフィール管理

アプリケーションは以下を提供する。

- プロフィールの作成
- プロフィール名の編集
- プロフィールの削除
- プロフィールの切り替え
- 任意メモの保存

プロフィールを削除する場合、そのプロフィールに属する進捗を削除してよい。
ただしUIでは明示的な削除操作として扱い、誤操作しにくい設計とする。

## 5.2 クエスト一覧

選択中プロフィールに対し、マスターに存在するクエスト系レコードを一覧表示できる。

少なくとも以下を表示可能とする。

- クエスト名／地図名
- 難易度
- オファー方法
- オファー都市
- 必要スキル
- 関連発見物
- canonicalな`quest_dependencies`に直接登録された前提Questの名称（地図等を含む）
- 達成状態

前提Questの名称表示は直接関係だけを列挙し、再帰的な祖先、AND/OR、達成状態を解釈・表示しない。

非アクティブなマスターの扱いはUI設計時に決めるが、データベースから物理削除しない。

## 5.3 クエスト進捗

プロフィールごとにクエスト達成状態を保持する。

状態モデルは次の通りとする。

- `quest_progress` に行が存在しない: 未達成
- `quest_progress` に行が存在する: 達成済み

v1ではクエスト進捗に「未報告」という状態を持たせない。

達成済みから未達成へ戻す操作も可能とする。

## 5.4 発見物一覧

選択中プロフィールに対し、発見物を一覧表示できる。

少なくとも以下を表示可能とする。

- 発見物名
- 発見物分類
- ランク
- 説明
- 時代
- ポイント
- 難易度
- 経験値
- 関連クエスト
- 発見状態
- 報告状態
- カード所有状態

## 5.5 発見物進捗

プロフィールごとに発見物進捗を保持する。

状態モデルは次の通りとする。

- `discovery_progress` に行が存在しない: 未発見
- 行が存在し `reported = 0`: 発見済み・未報告
- 行が存在し `reported = 1`: 報告済み

ただし、種別が`レリック`の発見物は報告対象外である。レリックは行の存在を発見済みかつ最終状態として扱い、`reported`の保存値を未報告または報告済みとして表示・集計しない。

発見済みから未発見へ戻す操作も可能とする。

未発見へ戻した場合、その発見物の `discovery_progress` 行を削除する。

## 5.6 カード所有状態

発見済みの発見物について、カードの現在所有状態を保持する。

- `card_owned = 1`: 所有
- `card_owned = 0`: 非所有

報告状態とカード状態は独立して変更できる。

新たに発見済みとして登録する通常操作では、ゲーム仕様に合わせ
`card_owned = 1` を初期値とする。ただしユーザーは直後に非所有へ変更できる。

ただし、種別が`レリック`の発見物はカード対象外である。レリックは`card_owned`を表示・集計せず、新規発見時には`card_owned = 0`を保存する。レリックの報告・カード操作は提供しない。

## 5.6.1 クエスト・発見物進捗の正方向連動

クエストと発見物の進捗連動は、ユーザーが未達成から達成、または未発見から発見済みへ
変更したイベントに対する入力補完とする。DB全体を常に同期させる制約ではない。

- Questを達成済みにしたときは、そのQuestに直接関連するactiveな発見物のうち未発見のものを、
  同一transactionで追加する。通常発見物は発見済み・未報告・カード所有とし、レリックは発見済み・報告対象外・カード対象外とする。既存の発見物進捗は
  `reported`、`card_owned`、`memo`を含めて変更しない。
- Discoveryを発見済みにしたとき、直接関連するactiveなQuestが1件なら同一transactionで
  達成済みにする。2件以上なら、ユーザーが1件または「クエスト進捗は変更しない」を選んで
  から保存する。選択したIDは保存時にもactiveな直接関係であることを検証する。
- Discoveryから自動達成したQuestを起点に、別のDiscoveryへ再帰的に連動してはならない。
- Questを未達成へ戻してもDiscovery progressを削除しない。Discoveryを未発見へ戻しても
  Quest progressを削除しない。報告状態とカード所有状態の変更もQuestへ連動しない。
- 自動連動は操作開始時に選択されていたプロフィールだけへ適用する。

Master Importによる関係更新時の再同期および既存進捗の一括backfillは行わない。

## 5.7 検索

少なくとも以下を検索できる。

- クエスト名／地図名
- 発見物名

v1ではSQLiteの通常検索を使用し、FTS5は必須としない。

## 5.8 絞り込み・並べ替え

少なくとも以下の絞り込みを提供できる設計とする。

### クエスト

- 達成／未達成
- 前提クエスト充足（選択中プロフィールのdirectな依存関係から導出）
- オファー方法
- 個別オファー都市（複数都市を含む元文字列を分割した各都市）
- 必要スキル名（rank条件は扱わない）
- 関連発見物の有無と分類（`quest_discoveries`を正本とする）

オファー方法は個別値に加え、大分類「クエスト」「地図」を選択できる。
「クエスト」は`冒険クエスト`・`交易クエスト`・`海事クエスト`のexact OR、
「地図」は`地理学`・`考古学`・`宗教学`・`生物学`・`美術`・`財宝鑑定`・`天文学`のexact ORとする。
他の個別オファー方法も維持し、大分類判定には名称の部分一致を使用しない。

関連発見物はDiscovery側の`関連クエスト`から構築されたrelationで判定し、Quest側の
`発見物`・`発見物種類`の原文から推測しない。「発見物あり」はrelationが1件以上、
「発見物なし」は0件を指す。分類はlinked Discoveryのいずれかが一致すれば対象とし、
inactiveな発見物へのrelationも含む。分類候補は一覧マスター全体のlinked分類から生成する。

前提クエスト状態は保存せず、Quest masterの依存関係と選択中プロフィールの達成状態から
`NONE`（前提edgeなし）、`SATISFIED`、`UNSATISFIED`、`UNKNOWN`を導出する。
通常Questの単一前提のみ完了／未完了を確定判定する。複数前提はAND/ORの組が
machine-readableではないため、通常Questの全前提が完了した場合のみ`SATISFIED`、
一部または全部が未完了なら`UNKNOWN`とする。地図等の特殊前提、欠損・不整合のある関係も
`UNKNOWN`とする。「前提を満たす」は`NONE`または`SATISFIED`を指し、スキル・名声・
国籍等を含む「受注可能」を意味しない。recursive ancestorの進捗整合性監査は別機能である。

必要スキルのうち名称が `語` で終わるものは、rankではなく習得の有無を要求する
language skillとして扱う。
必要スキル名を選択した場合、そのスキルの正規化された要求rankを数値で低い順・高い順に
並べ替えられる。数値rankを持たないスキルでは並べ替えを利用できない。rankが未記載の行は
両方向とも数値rankのある行の後に置く。この並べ替えはQuest masterの要求値を対象とし、
プロフィールの習得スキルや受注可否は判定しない。

### 発見物

- 発見物分類
- 未発見
- 発見済み・未報告
- 報告済み
- カード所有／非所有

一覧は主要列で並べ替え可能とする。

マスターデータ画面の下部には、データ提供元である「大航海時代データベース」と
データを収集・整理・更新・公開してきたコミュニティへの謝辞を表示する。
外部サイトはユーザー操作時のみ既定ブラウザーで開く。この謝辞は公式・公認・提携・保証を意味しない。

## 5.9 達成度の可視化

選択中プロフィールについて、少なくとも以下を表示する。

- 発見物総数
- 発見済み数
- 全体発見率
- 発見物分類ごとの総数
- 発見物分類ごとの発見済み数
- 発見物分類ごとの達成率
- 未報告発見物数
- 発見済み発見物のうちカード所有数
- 発見済み発見物のうちカード所有率
- プロフィールごとの報告済み発見物から算出した冒険勲功値（判明分）

クエストについても、全体の総数・達成数・達成率を表示可能な設計とする。

集計結果は原則としてSQLiteクエリで算出し、v1では集計専用の永続テーブルを持たない。

概要の発見物分類別カードは、category IDで指定した発見物一覧への移動入口とする。
移動時は発見物一覧の検索・状態・カード所有filterを既定値へ戻し、指定分類だけを適用して
1ページ目から表示する。現在選択中のプロフィールは維持し、存在しない分類IDは「すべて」へ戻す。
移動指定は一度だけ適用する一時的なUI stateとし、永続化しない。

達成率・発見率および分類別達成度は、原則として `is_active = 1` の現在有効な
マスターだけを分母・分子の対象とする。非アクティブなマスターに紐づく既存進捗は
保持するが、現在の集計には含めない。

冒険勲功値は、プロフィールの報告済みかつ報告可能な発見物について、
`discoveries.experience` の判明値をSQLiteクエリで都度合計する派生値とする。レリックは
報告対象外のため除外し、非アクティブ化された発見物でも報告済みなら過去の値を合計へ残す。
`experience = NULL`は合計に含めず、UIでは「冒険勲功値（判明分）」として表示する。爵位thresholdや
爵位判定はこの機能の対象外とする。

## 5.10 マスターデータの手動インポート

ユーザーはローカルファイルから、以下のGVDB公開データを明示的にインポートできる。

- `quests.csv`
- `discovery_items.csv`

GUI上で対象datasetのローカルファイルを選択し、内容の解析結果を確認した後、明示的な
インポート操作によってのみマスターデータを更新する。

## 5.11 バックアップと復元

ユーザーはGUIからSQLiteデータベース全体の整合したバックアップをローカルファイルへ
手動保存できる。バックアップにはマスターデータ、プロフィール、クエスト進捗、発見物進捗、
インポート履歴を含む現在のDB全内容を含める。

ユーザーは検証済みバックアップを選択し、現在のDBがバックアップ時点へ置き換わる旨を
確認した後にのみ復元を実行できる。復元後はアプリケーションを再起動する。

バックアップ作成は現在DBを変更してはならない。復元対象は現在DBを変更する前に整合性、
必須schema、migration互換性を検証し、復元失敗時は操作前のDBを維持する。自動、定期、
クラウド、ネットワーク経由のバックアップはv1では実装しない。詳細な安全規則は
`backup-restore.md`を正本とする。

アプリケーション自身がGVDBから自動ダウンロードしてはならない。

インポート仕様の詳細は `data-import.md` を参照する。

## 5.12 データ保存場所

アプリケーションは標準保存場所（AppConfig directory）を既存利用者と互換に維持する。ユーザーは設定画面から、ローカル固定NTFS上の空directoryへDB全体を安全に移行できる。移行時は現在DBの整合したsnapshotを作成し、旧DBを削除しない。保存場所が利用できない場合は別のDBを自動作成せず、Recovery画面で再試行、検証済み既存rootの再指定、またはpending移行のrollbackを行う。詳細は`data-root.md`を正本とする。

## 6. 状態遷移

## 6.1 クエスト

```text
未達成
  │ 達成として登録
  ▼
達成済み
  │ 未達成へ戻す
  ▼
未達成
```

DB表現:

```text
未達成   = quest_progress 行なし
達成済み = quest_progress 行あり
```

## 6.2 発見物

```text
未発見
  │ 発見として登録
  ▼
発見済み・未報告
  │ 報告済みに変更
  ▼
報告済み
```

報告済みから未報告へ戻す操作も可能とする。

発見済みを未発見へ戻す場合は `discovery_progress` 行を削除する。

## 6.3 カード

```text
所有 <-> 非所有
```

カード状態は発見物が発見済みである間だけ管理する。

## 7. データ保護要件

以下は必須要件とする。

1. マスター更新でプロフィールを削除しない。
2. マスター更新でクエスト進捗を削除しない。
3. マスター更新で発見物進捗を削除しない。
4. GVDB側のマスターからレコードが消えても、ローカルでは物理削除せず非アクティブ化する。
5. マスター更新失敗時は途中状態を残さない。
6. データベースファイルをコピーすることで、ユーザーデータをバックアップできる構造とする。

## 8. 非機能要件

### 8.1 オフライン動作

通常利用は完全にオフラインで動作すること。

### 8.2 性能

数千〜数万件規模のマスターを想定する。

通常の一覧、絞り込み、検索、進捗更新がローカルPC上で十分な応答速度を持つこと。

v1では過剰なキャッシュや検索エンジンを導入しない。

### 8.3 信頼性

- SQLiteの外部キー制約を有効にする。
- 複数テーブルにまたがるマスター更新はトランザクションを使用する。
- 外部ファイルは検証後にDBへ反映する。
- 不正な入力を理由に既存ユーザーデータを変更しない。

### 8.4 保守性

- DB変更はmigrationで管理する。
- UIとSQLを分離する。
- マスター取込処理を独立したモジュールとして実装する。
- 仕様変更時は対応するドキュメントも更新する。

## 9. v1で対象外とする機能

以下はv1の対象外とする。

- Webサービス化
- クラウド同期
- ユーザー認証
- 複数PC同期
- スマートフォン同期
- GVDBからの自動ダウンロード
- GVDBへのデータ送信
- GVDBのスクレイピング
- カード取得／消失イベント履歴
- ゲームアカウント単位の管理
- SQLite FTS5による全文検索
- OCR等によるゲーム画面からの自動進捗取得
- 他ユーザーとの進捗共有

## 10. 将来拡張候補

v1のDBを壊さず追加可能な候補として、以下を想定する。

- カード取得・消失履歴
- アカウントとキャラクターの階層管理
- より高度な検索
- 前提クエストのグラフ表示
- 発見方法別の分類
- インポート差分プレビュー
- バックアップ／リストアUI

これらは現時点では実装しない。
