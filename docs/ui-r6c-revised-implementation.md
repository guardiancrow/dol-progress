# UI-R6C改訂実装報告

前提クエストの達成記録漏れを確認するため、既存の前提名セルからUI-R5B/Cと共通の詳細領域を開く構成へ改訂した。登録は既存候補に該当する直接関係だけに提供する。実装とローカル検証は完了し、Ownerの実装レビューと実アプリでの画面確認を待つ。

## 改訂の経緯と前案の保全

前案は汎用的な前提・後継探索を中心としていたため、Ownerレビューで不承認となった。その後に承認された再設計と、今回の追加条件を基本仕様として実装した。前案のテスト成功を、新しいUI方針の承認として扱っていない。

ブランチは`feat/ui-r6c-quest-navigation`、HEADは`0c21ffa`のままである。開始時の未コミット11ファイルを`tmp/ui-r6c-revised-review/before/`へコピーし、manifestのSHA-256で全件の一致を確認した。前案の5つのソース・テストは`tmp/ui-r6c-revised-review/retired/`へ個別に移して保全した。テストの保全コピーには`.snapshot`を付け、通常のVitestに混入しないようにした。skip・ignoreやテスト設定による除外は追加していない。

[前案の実装報告](ui-r6c-implementation.md)は原文のまま保全した。本報告と[要件定義](requirements.md)の「前提クエストの記録確認（UI-R6C改訂）」が今回の改訂内容に対応する。破壊的なreset・一括削除は行っていない。公開済みv0.5.0のtag、正式source、Release、配布成果物、承認記録、配布スクリプトと版番号は変更していない。commit・push・PR作成も行っていない。

## 最終的な操作仕様

一覧は既存の9列とし、「前提クエスト」セルに表示済みの名称列挙全体を一つのボタンにした。空欄には操作を追加せず、原文だけの参照で名称を補完しない。入口の文字列・色は候補の有無で変えず、アイコン・状態バッジ・件数・ツールチップを追加していない。読み上げ名は、そのセルの前提名と一覧に見えている対象クエスト名だけで構成する。

前提名を操作すると「前提クエストの記録確認」を開く。現在確認しているクエスト、その直接前提、選択プロフィールの達成記録、必要な確認理由を表示する。読取中・保存中・失敗中は「達成記録は未確認」とし、未達成と確定しない。プロフィール未選択時は従来の選択案内を表示する。

直接前提Bにも正規化された直接前提がある場合だけ「Bの前提を確認」を表示する。操作後に次の前提を描画し、「前の確認に戻る」で戻れる。既出の内部IDへ進もうとした場合は遷移を止める。履歴は一時的な表示履歴だけで、プロフィール・マスターの切替で破棄する。20件を超える直接前提は独立してページ分割する。開閉・段階移動にDB問い合わせは追加しない。

## 表示・診断・候補・登録の分離

表示する名称は既存の`resolveDirectPrerequisites()`が返す正規化済みの直接関係を使用する。欠損先を作らず、原文だけの参照を一覧へ補完しない。表示名が一致しても内部IDとGVDB IDを区別する。

構造診断には、既存の確認候補索引が保持する除外理由と、実際の正規化された直接関係の情報を使用する。複数前提、欠損、不一致、不正な原文、自己参照、循環または未解決の参照等の理由を表示できる。診断結果を渡せない場合は確認不能とする。循環そのものとその影響を推測で区別せず、既存の診断が示す範囲で説明する。

これらの理由から登録を許可する処理は設けていない。登録候補は既存の`buildPrerequisiteReviewIndex()`と`derivePrerequisiteProgressReview()`だけで作成する。両関数、`prerequisites.ts`、`directPrerequisites.ts`は変更していない。一般的な全前提の表示用索引へ、確認候補索引を転用していない。

## 達成登録の許可条件とUI-R5B/Cとの統合

Aの達成記録があり、Bが未達成で、AとBが既存の単一直接前提の候補に該当するときだけ、Bの登録操作を提示する。複数前提・地図・特殊クエスト・inactive・構造異常などの既存の除外条件を緩めていない。

詳細側では、対象Aの達成記録を確認できる状態で利用者が前提を開いたことも保持する。未達成のBの詳細を先に開き、その後Bが達成済みになっても、Cの登録操作は自動提示しない。利用者がBの前提を開き直すか「前提を再確認」を押した後で、BとCの直接関係を改めて判定する。進捗が更新中・未確認になった場合や、対象の達成記録がなくなった場合も、この詳細からの登録には明示的な再確認を必要とする。

両方の入口は同じ確認画面と`reviewCompletion`を使い、プロフィール・対象ID・現在も候補であること・snapshot・読取世代・更新revisionを確定直前に照合する。保存は既存の`updateCompletion()`と`completeQuestWithLinkedDiscoveries()`を使用し、対象1件だけを登録する。他の前提を再帰的に登録しない。既存の発見物連動・transaction・既存進捗を上書きしない契約は変更していない。

保存成功後は達成済みIDを一括再取得し、同じプロフィールとマスターの世代・読取世代・更新revisionであることを確認して表示と候補を再計算する。保存の結果不明は成功と通知しない。保存成功後の再取得失敗は区別して案内し、計算完了の成功通知を出さない。保存中は通常一覧からの競合更新も抑止する。取得先が同じ配列を再利用する場合も、マスター世代ごとに前提状態と直接前提を再計算する。

## ネタバレ防止とフォーカス

`MasterInfoPopover.tsx`は変更していない。備考・説明を前提詳細へ転載せず、既存の(i)操作後にだけ既存ポップアップで描画する。新しい表示用のクエスト識別情報には備考・原文を含めない。

後続参照は内部検証にだけ使用し、診断の文言にも後継の名称・ID・件数を含めない。直接前提Bのさらに先にある複数前提の診断は、Bを明示的に開くまで表示しない。B自体のinactive・特殊条件と、Bの前提関係の診断を分けた。閉じた詳細は非表示DOMに内容を保持せず、本文を描画しない。未知の後継・未開示の祖先・備考が本文や属性へ漏れないこと、詳細のIDが開く前と閉じた後のDOMに残らないことをテストした。

Tab・Enter・Spaceで操作でき、開く際は現在の確認対象、登録開始時は確認領域へフォーカスを移す。Escapeは確認のキャンセルを優先し、確認がなければ詳細を閉じる。保存中に保存をキャンセルしたとは扱わない。確認・保存中の詳細切替と段階移動を抑止する。閉じる際は起点へ、検索や候補解消で起点がなくなった場合は検索欄または残存する一覧操作へ戻す。

## 画面の実測

headless Edgeの合成データ画面で、800×600、1024×768、1920×1080、通常表示とテーブル優先表示を測定した。実ユーザーDB・実CSV・GVDBへのアクセスは行っていない。

| 800×600の状態 | 実測 |
| --- | --- |
| 列数・通常行高 | 9列・44px。前提名を通常のspanに置換した比較表示でも44px |
| 通常表示で詳細を開いた場合 | 詳細約108px、一覧160px。ページ送りは画面内 |
| テーブル優先表示の確認・保存後 | 詳細210px、一覧約196px。ページ送りは画面内 |
| 通常文字倍率のはみ出し | ページ全体の縦横はみ出し0。メイン領域の縦はみ出し0 |
| 文字倍率200% | 新詳細の高さ192px。メイン領域と詳細内のスクロールを利用し、Tabでキャンセル・確定ボタンが画面と詳細領域の双方に収まることを確認。ページ全体の横はみ出し0 |

200%の検証は、合成ブラウザー画面のroot font-sizeを200%にして行った。一覧の文字・行とページ操作も拡大されるため、ページ送りを含むメイン領域は内部スクロールになる。通常倍率と同じ行数が収まるという意味ではない。閉じた後の起点へのフォーカス復帰も確認した。Windowsの表示倍率・DPI別の実アプリ検証は今回実施していない。測定スクリプト・画面・画像・`measurements.json`・各ログは`tmp/ui-r6c-revised-review/`に保全した。

## Ownerによる動作確認

1. 開発ブランチで`npm run tauri dev`を起動し、確認用プロフィールを選ぶ。保存を試す場合は既存のバックアップ手順で事前に保全する。
2. 800×600で9列の一覧を確認する。前提が空欄のセルには操作がなく、前提名があるセルだけをクリック・Enter・Spaceで開けることを確認する。
3. 開いた対象と直接前提の名前・ID・達成記録を確認する。複数前提や不整合のある関係でも、既知の名前が読めることを確認する。
4. さらに前提がある場合だけ「…の前提を確認」があることを確認する。押した場合だけ次の前提が表示され、戻れることを確認する。後継・目標・経路や全体件数が表示されないことも確認する。
5. 既存候補に該当する、達成済みAと未達成Bの直接関係を開く。確認画面のプロフィール・対象名・ID・発見物連動を読み、まずキャンセルして記録が変わらないことを確認する。
6. 実際の記録漏れを修正する場合だけ再度確認して確定する。Bだけが登録され、再取得後に候補が更新されることを確認する。Bの前提を自動的に開かないことも確認する。
7. 未達成Bの前提を先に開いた場合は、Cの登録操作がないことを確認する。Bの達成記録を変更した後は、明示的な「前提を再確認」または開き直しを必要とすることを確認する。
8. 既存の「進捗の確認候補」と新詳細を切り替える。確認・保存中の不正な切替ができず、既存候補のフィルターとページ操作が維持されることを確認する。
9. 検索・絞り込み・並べ替え・一覧のページ位置・表示件数を設定し、開閉後も保持されることを確認する。起点の行を検索等で消した場合も、閉じると残存する操作へフォーカスが戻ることを確認する。
10. (i)を開かない限り備考・説明が前提詳細に出ないこと、詳細を閉じると内容が残らないことを確認する。TabとEscape、テーブル優先表示、文字倍率200%でもキャンセル・確定・閉じる操作へ到達できることを確認する。
11. プロフィール切替とマスター更新で、以前の表示履歴・確認が破棄されることを確認する。

保存・再取得失敗、遅延応答、欠損・循環等は合成データのテストで再現した。手動確認のために実DBを壊す必要はない。
